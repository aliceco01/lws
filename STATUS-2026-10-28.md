### jobset#1367: facts re-verified at LWS main `4f2bfdc`

The question (andreyvelich, 10-26): "Do we also support `scheduling.k8s.io/workload-name` annotation in LWS like we did for Job?" kannon92 (10-27) replied to the separate PodGroup vs CPG integration question with "Yea I think that makes sense." There is no reply from you yet.

- LWS never reads `scheduling.k8s.io/workload-name`. `git grep` on main finds no occurrence at all.
- Delegation works through `scheduling.k8s.io/group-template-name` on the LWS (`pkg/schedulerprovider/interface.go:46`).
  - `findDelegatedWorkload` (`pkg/schedulerprovider/kubernetes_provider.go:697-744`) walks the LWS controller-owner chain.
  - At each hop it lists Workloads indexed by the owner UID and picks the one whose `spec.controllerRef` matches the owner's group, kind and name.
  - So it finds the Workload by ownership, not by name.
  - It returns `"... requires a controller owner"` when the LWS has none (`:700`).
- Also new since the brief, all on main:
  - more than one matching Workload is an error (`:724`)
  - an owner whose UID changed is an error (`:739`)
  - #1163 (`8fc6676`) forbids swapping the controller owner of a delegated LWS
- `scheduling.k8s.io/parent-compositepodgroup` is declared (`interface.go:50`) but not honored yet (`TODO(phase2)` at `kubernetes_provider.go:265`).
- `leaderworkerset.sigs.k8s.io/workload-name` (`kubernetes_provider.go:61`) is internal. LWS sets it on its own pod templates (`leaderworkerset_controller.go:1160`, `pod_controller.go:1637`).

### kueue#17500, reply in the "Rollout churn" thread (pajakd and vivekk16)

Thread: https://github.com/kubernetes-sigs/kueue/pull/17500 (KEP README, "Rollout churn")

> This holds when the role's `maxUnavailable` is at least 1, but with `maxUnavailable: 0` I think the rollout can stall. With 0, the DisaggregatedSet planner drains an old replica only once a target replica is Ready. The availability floor is `desired - maxUnavailable` (`pkg/controllers/disaggregatedset/planner_state.go:202-203` in lws main) and old-side drains must keep it (`planner_availability.go:146-159`). If Kueue keeps the new-revision Pod gated until the Pod it replaces is gone, the new replica never gets Ready, so the old one never drains. The planner's unavailable fallback does not help here, because it only fires for Pods the scheduler marks `Unschedulable` (`executor.go:443-451`), and a gated Pod reports `SchedulingGated`. The bootstrap surge step adds one more replica, which Kueue also leaves gated.
>
> Two ways out I can see: require `maxUnavailable >= 1` for Kueue-managed roles in the webhook, or let the reconciler adopt one surplus Pod per role while a rollout is in progress and size the slice Workload for it. This is from reading the code at lws `4f2bfdc`, not from a cluster run.

Unverified: a Kind run with Kueue would confirm the stall. The session did not run one.

### llm-d-router#3456, note after yankay

Thread: https://github.com/llm-d/llm-d-router/pull/3456 (`affinity.go`)

> Adding to yankay's point, the Anthropic path has the same gap. `writeAnthropicContent` (`affinity.go:108-116`) hashes only `text` blocks, so image and document blocks and the content of `tool_result` blocks drop out of the key too. On the chat side, `Content.PlainText()` keeps only `text`, so audio and video blocks go the same way as images.
>
> On the fix, a weighted random fallback keeps load spread, but it also breaks stickiness for a multi-turn multimodal session without a session header, since every turn draws again and the turns can split across revisions. Hashing a stable identity of each non-text block (the URL, or a digest of inline data) keeps the turns of one session together and still spreads sessions that differ only by image.
